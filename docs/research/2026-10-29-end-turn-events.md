# 结束回合的事件记录与交互边界调研

本文核对游戏接口，提出 `end_turn` 的候选设计；尚未实现事件战报或选择动作，不改变现有工具契约。

## 结论

建议建立供游戏动作共用的事件记录与停止条件层：调用正常动作流程，在自动结算期间持续记录已发生且玩家可感知的效果，到下一可行动阶段、必须作出的选择或已确认的战斗结果时返回。`end_turn` 使用这一层，不逐个模拟卡牌、power、遗物和敌人的规则。

游戏已有 `CombatHistory`、角色事件和动作等待选择的通知，但没有核实到能够直接返回完整、符合本项目信息边界的战报接口。应组合这些来源，补充历史缺失的事件，并统一过滤和去重。不能承诺仅接一个历史接口便覆盖所有机制。

## 当前实现的边界

`GameAdapter.Execute` 提交 `EndPlayerTurnAction`，随后等待战斗不再进行、战斗对象被替换，或玩家回合数增加且 `CanEndTurn()` 为真，最后返回一次稳定观察。等待上限为 25 秒；稳定观察最长再等 2 秒。

当前实现不收集期间事件，也不识别必须作出的选择。`CanEndTurn()` 要求玩家处于 `Play` 阶段且手牌模式为 `Play`；回合开始选牌可能使等待条件一直不成立，最终超时。超时只表示未确认执行完成，不能自动再次结束回合。

`EndPlayerTurnAction.ExecuteAction` 本身只标记玩家准备结束回合，并不等待整个回合转换。因此该 action 的完成任务、动作执行器暂时空闲或画面短暂稳定，都不能单独证明自动结算完成。

## 已核实的可复用接口

| 来源 | 已核实成员及行为 | 使用限制 |
| --- | --- | --- |
| 战斗历史 | `Combat.History.CombatHistory.Entries`、`Changed`；包含出牌开始/完成、受伤、攻击、格挡、抽牌、弃牌、消耗牌、生成牌、获得 power 等条目 | 没有独立死亡、复活、治疗及完整 power 变化条目；不是完整事件流 |
| 角色事件 | `Entities.Creatures.Creature` 的 `CurrentHpChanged`、`MaxHpChanged`、`BlockChanged`、`PowerApplied`、`PowerIncreased`、`PowerDecreased`、`PowerRemoved`、`Died`、`Revived` | 变化不一定携带原因；订阅不能等到下一帧才开始，否则会遗漏中间变化 |
| 战斗对象变化 | `Combat.CombatState.CreaturesChanged`，以及 `CombatManager.CreaturesChanged` | 需要同步订阅新增角色、解绑离场对象；这些通知的时机不完全相同 |
| 战斗生命周期 | `CombatManager.CombatWon`、`CombatEnded`、`TurnStarted`、`TurnEnded`、`PlayerActionsDisabledChanged` | 单个回合通知不能证明所有选择和自动效果已完成；`IsInProgress` 提前变为假也不等于胜利流程已经完成 |
| 选择暂停 | `GameActions.GameAction.BeforePausedForPlayerChoice`、`State == GatheringPlayerChoice`；`ActionQueueSet.ActionEnqueued` 可用于跟踪新 action | 暂停通知先于状态赋值，而且选择 UI 可能尚未建立；应等待相应选择入口可读，不能在回调内立即读取页面 |
| 选择上下文 | `PlayerChoiceContext.LastInvolvedModel`；`PushModel`、`PopModel` 保留嵌套来源；`HookPlayerChoiceContext`、`GameActionPlayerChoiceContext` 将选择接入动作队列 | 历史条目不普遍携带此上下文；要补全来源，需要在有上下文的命令入口保存当时的元数据 |
| 状态通知 | `CombatManager.StateTracker.CombatStateChanged` | 下一帧合并通知，不是逐事件记录；同一帧死亡再复活等中间过程可能被合并 |

`CombatHistoryEntry.Description`、`HumanReadableString` 是内部描述，可能包含模型 ID 和敌人的 `Move.Id`；不应原样传给 LLM。条目还引用可变对象，事件发生时应复制所需标量、名称和稳定对象标识，不能等调用结束再解引用。

### 历史不足以承担完整战报

1. `CombatManager.EndCombatInternal` 会在胜利流程中清空历史，然后才触发 `CombatWon`、`CombatEnded`。仅在工具结束时按索引切片会丢失此前事件。
2. `CreatureCmd.Damage` 写入 `DamageReceived` 的条件为 `IsInProgress && !IsEnding`。伤害导致最后一个主要敌人死亡、使 `IsEnding` 成立时，该伤害条目可能不被写入。
3. `DoomPower.DoomKill` 直接走 `CreatureCmd.Kill`，不能把它伪装成一次普通伤害。
4. `DamageResult.WasTargetKilled` 的说明明确包含随后复活的情况，不能用它直接宣告最终死亡或胜利。

## 方案比较

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 只比较前后观察 | 简单，适合结果核对 | 无法解释先受伤后治疗、死亡再复活、自动出牌及多次攻击；丢失顺序和来源 |
| 仅收集 `CombatHistory` | 已有结构化条目，接入量较小 | 缺事件、可能缺致命一击、胜利时清空，无法完整满足需求 |
| 历史、原生事件和少量命令层记录组合 | 复用游戏规则，记录中间过程，可扩展到其他动作 | 需核对各来源时序、去重和可见性，并通过复杂场景验证；推荐 |

## 候选设计

### 统一记录，按动作分段

由独立记录器收集事件，动作执行层决定何时返回；Python MCP 层只做协议校验与输出投影。记录器不改变游戏状态、不替玩家选择，也不在游戏线程执行外部 I/O。

提交动作前建立记录起点和战斗身份，订阅历史及必要事件。历史变化时及时复制新增条目到自己的有界缓冲区，不能依赖游戏历史永久存在。对死亡、复活、治疗、power 减少/移除等缺项使用角色事件；对历史遗漏的最终伤害等使用经过验证的命令层记录补齐。

每类事实明确一个主要记录来源，其他来源用于补缺或校验。一次伤害不能同时作为“攻击条目”“受伤条目”和“HP 下降”输出三次；实际 HP 变化也不能一律称为伤害。记录序号表示捕获顺序，因果关系另行记录，不能仅按相邻顺序推断。

伤害命令有多层重载，并会触发嵌套伤害。补录点须能在致命伤害和后续死亡效果之间确定顺序；不能简单等待最外层异步方法返回，再把全部伤害追加到日志尾部。最终选择哪个补录点、如何关联已存在历史条目，需要实施时用实际调用轨迹验证。

来源优先使用明确的 card source、`LastInvolvedModel` 和经过核实的当前效果上下文。必须区分“谁造成效果”和“哪张牌、哪个 power 触发效果”。无依据时来源保留未知，不能因为上一条是某个敌人的动作，就把后续反伤、状态伤害都归给它。没有上下文的死亡命令也不能仅凭目标有灾厄便归因为灾厄。

### 在首次需要决策时返回

正常返回原因建议区分为：

| 候选值 | 边界 |
| --- | --- |
| `player_ready` | 下一玩家可行动阶段成立，相关自动流程已经完成，没有待选择或待结算动作 |
| `choice_required` | 本地玩家确有尚未完成的选择，且对应界面已经可以读取；无论它发生在回合结束、敌方行动还是回合开始 |
| `combat_won` | 由游戏确认的本场战斗胜利；不表示整局通关 |
| `combat_lost` | 由游戏确认的本场战斗失败；不能仅凭 HP 暂时为零认定 |

战斗身份变化、退出、加载与其他中断另外表达，不能当作胜利。超时、取消及记录不完整也须明确标识；如果已经提交动作，不得自动重发。遇到普通暂停菜单不应伪报 `choice_required`。

停止判断组合游戏流程、动作状态、待选择状态和 UI 可用性。`TurnStarted` 作为信号，不能作为唯一条件；队列空闲同样不能替代流程完成。画面稳定等待只用来得到一致的终态观察，不能定义逻辑完成。

遇到暴政时，`end_turn` 返回此前已发生的事件和“需要选择”的边界信息，不能包含尚未选择的结果。可包含选择来源名称，供调用方理解为何停止；候选牌、数量和确认动作属于后续选择接口。游戏原生暂停的结算任务保留，后续选择工具完成选择后收集自动续跑的事件，直到下一个决策点。无需再次调用 `end_turn`，也不能把读取选择界面当作完成选择。

当前尚无选择工具；第一阶段即使只实现停止和明确告知，也必须说明无法自动继续，不能等待 25 秒后只报超时。未知选择界面保守返回“当前不支持的选择”，不代选。

### 输出内容与信息边界

建议输出“有序事件 + 停止原因 + 最终基础观察”，JSON 仍使用英语。字段名和具体 schema 在实施设计时确定，不将示意当作现有接口。

- 常用事实包括自动出牌、每次攻击/受伤的实际格挡和 HP 损失、治疗、power 变化、牌的公开移动/生成、死亡、复活及战斗结果。重复同一次效果的开始/结束事件不必全部交给 LLM。
- 保留影响决策的先后关系和对象身份；同一怪物死亡再复活沿用同一实例标识，另一个新生成的同种怪物不能复用身份。自动重放和多段攻击不能静默合成一次。
- 来源名称可说明“惊逃使某牌自动打出”“凋萎造成实际伤害”；不必每次附送完整卡牌正文和所有 power 解释。无法确定来源时仍可记录已核实结果。
- 区间事件属于动作期间的可感知历史，和采样时的静态观察分开。不能因此开放隐藏抽牌顺序、敌人未来动作、内部状态机、隐藏 power 或未公开的生成结果。
- 敌人塞牌只输出实际公开的信息。若动画/提示公开了牌名和数量，可记录；若仅有背面入堆动画或计数，则不能从内部生成条目补出名称、位置或将来抽取顺序。
- 不把所有钩子调用写成触发事件：游戏会遍历并调用大量没有实际效果的默认钩子。触发记录须有实际效果或已核实的公开提示依据。
- 为异常循环设置缓冲上限，达到上限明确标记不完整；不能静默截断后声称已完整记录。

建议内部为各动作共用记录器和游标，不要求立刻把全部历史暴露成新 MCP 工具。记录应能在客户端超时或断线后供恢复读取；准确恢复方式需连同动作结果存储与读取确认机制设计，不能仅靠重试动作，也不能把一次读取默认为永久消费。

## 示例机制的落点

| 机制 | 已核实路径 | 对设计的要求 |
| --- | --- | --- |
| 惊逃 `StampedePower` | `AfterAutoPostPlayPhaseEntered` 选择手中攻击牌并调用 `CardCmd.AutoPlay`；`CardPlay.IsAutoPlay` 区分自动出牌 | 记录实际打出的牌、目标及效果；不能提前读取随机选择结果 |
| 凋萎 `Wither` | `OnTurnEndInHand` 调用 `CreatureCmd.Damage`，携带该牌作为来源 | 记录实际损伤及可能导致的战斗失败；不按牌面数值自行计算 |
| 敌人攻击或塞牌 | 历史攻击/受伤/生成牌条目，加必要的伤害补录及公开展示证据 | 记录实际结果；不把内部 move ID 和未展示牌堆位置当作观察 |
| 灾厄 `DoomPower` | `BeforeSideTurnEnd`、`DoomKill`、`CreatureCmd.Kill` | 记录死亡事实，不虚构普通伤害；精确原因需在调用处保留证据 |
| 残杀千足虫 `DecimillipedeSegment` | `ReattachPower` 阻止死亡后移除；`ReattachMove` 调用 `DoReattach`，通过 `CreatureCmd.Heal` 复活 | 分别记录死亡与复活；依据游戏战斗结果判断胜负，不能见零血就结束 |
| 滚石 `RollingBoulderPower` | `AfterPlayerTurnStart` 等待 VFX 命中并等待伤害任务，再更新计数 | 纳入回合开始自动结算；不能看到回合数增加就提前返回 |
| 暴政 `TyrannyPower` | `AfterPlayerTurnStart` 等待 `CardSelectCmd.FromHand`，选择完成后调用 `CardCmd.Exhaust` | 选择出现时返回，不等消耗发生。当前版本效果是“消耗”手牌，不是从永久牌组删除 |

`CardSelectCmd.FromHand` 在没有候选，或无需人工确认且候选数不超过最低选择数等情形会自动完成。因此应检测实际需要交互的暂停与界面，不能见到选择函数调用便一律提前返回。

## 后续实施的验证范围

至少覆盖：普通敌方回合；惊逃击杀最后一个敌人；凋萎致死；敌方致命攻击；灾厄击杀；千足虫死亡再复活；滚石在玩家回合开始时击杀；暴政停在选择前；回合结束选择；自动出牌引发嵌套选择；无需人工选择的自动完成分支；多段攻击及反伤去重；胜利清空历史后记录仍存在；新敌人加入；超时/断线恢复；隐藏牌名与抽取顺序不泄露。

先用确定的测试事件序列验证记录、去重和停止判定，再在隔离游戏存档中验证钩子时序、动画及 UI 就绪。编译和模拟测试不能替代这些游戏内验证。

本次完成的是程序集、资源和现有代码核对，没有修改工具实现，没有执行游戏内动作，也未验证候选方案的完整运行时覆盖率。
