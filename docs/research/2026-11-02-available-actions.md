## 结论

### 事件中的遗物查看确实不可用

`RelicInspection.VisibleHolders()` 首先要求以下条件之一成立：

- `CombatObservation.Status() == "visible"`；
- 暴露的先古之民界面；
- 暴露的商店界面。

普通事件、火堆、宝箱、非战斗奖励和非战斗地图没有通用入口。即使遗物图标可见且能接受鼠标事件，也在检查实际 holder 前返回 `null`。

`GameAdapter.AvailableTools()` 和 `inspect_relics` 请求都使用这个函数，因此列表与实际拒绝行为一致：**不能通过仅添加工具名修复**。基础观察仍可展示遗物名称、计数和熔化状态，不代表详情入口已经放行。

原生 `NRelicInventoryHolder.OnFocus()` 直接创建 `_relic.Model.HoverTips`，自身没有上述房间白名单。建议以当前可见、可悬停的遗物栏为准，复用通用界面遮挡规则，保留 holder 启用、鼠标事件、图标纹理及实际可见性检查。各场景仍须实测原生悬停和遮挡，不能仅凭图标存在放行。

### 非战斗牌组查看也尚未支持

`GameAdapter.CanInspectDeck()` 明确要求正在战斗；`InspectDeck()`、`CardView.Current`、`DeckView.Current` 及打开后的检查也沿用战斗上下文。因此事件、火堆、宝箱、商店和非战斗地图未列出 `inspect_deck`，目前调用也会失败。

原生 `NTopBarDeckButton.OnRelease()` 使用 `NDeckViewScreen.ShowScreen(_player)`，自身没有战斗限定。这里属于需要补齐的查看能力，不是动作列表丢失。实现时应同时处理非战斗页面识别、打开、关闭、切换地图及原场景恢复，避免只改入口后无法关闭页面。实际按钮可见且启用仍是前提；不能将任意选牌弹层都当作可打开牌组的场景。

### 全部 17 个详情工具均未返回可用动作

下表列出的 17 个 `inspect_*` 工具都没有返回 `available_actions`。Mod 的详情结果通常只序列化专用字段，Python 详情 reader 也不保留动作列表；即使输入中提供该字段，宝箱 reader 仍会移除它。

这并不使工具后的动作不可执行：成功详情读取仍刷新动作许可。当前可使用 `get_observation({"preset":"actions_only"})` 获取工具名，但仅查看详情的调用者不能从本次结果发现后续入口。尤其 `inspect_map`、`inspect_deck`、`inspect_pile` 会改变页面，返回关闭入口更有价值。

| 工具 | 当前可用条件与判断 |
| --- | --- |
| `inspect_hand` | 可见战斗手牌，且不在出牌过程；事件没有手牌时不列出合理 |
| `inspect_ui` | 可见战斗界面；目前只实现战斗界面的悬停说明，非战斗不列出合理 |
| `inspect_combatants` | 可见战斗背景、存在本地玩家、手牌不在出牌；普通事件不列出合理 |
| `inspect_potions` | `RunUi.TopBarReadable()`，且药水栏、所有槽位可见并启用；已有非战斗入口，未发现普通事件白名单遗漏 |
| `inspect_relics` | 战斗／先古之民／商店白名单，再检查遗物栏；存在上述能力缺口 |
| `inspect_targets` | 当前能处理可见手牌或药水，且至少有一种支持的目标类型；需具体卡牌或槽位参数，不保证每个参数都合法 |
| `inspect_selection` | 受支持的本地卡牌选择，候选页面可见；被覆盖或切到战场时须先返回选择页 |
| `inspect_rewards` | 本地奖励页面就绪；没有打开的奖励列表时不列出合理 |
| `inspect_rest_site` | 本地火堆页面就绪 |
| `inspect_treasure` | 宝箱页面暴露；读取条件比取走遗物更宽，允许展示尚不能点击的状态 |
| `inspect_shop` | 单人商店库存已打开、暴露且不在开关动画；仅看见商人时不列出合理 |
| `inspect_ancient` | 暴露的单人先古之民界面；不必等选项已经可点击 |
| `inspect_event` | 暴露的单人普通事件，或已经就绪的占卜界面；占卜是同一工具的另一分支 |
| `inspect_run_result` | 原生结算／解锁流程就绪；被遮挡或过渡中不列出合理 |
| `inspect_deck` | 仅单人战斗及其支持的覆盖页面；存在上述非战斗能力缺口 |
| `inspect_pile` | 可查看战斗中的抽牌／弃牌／消耗堆；只列工具名，具体牌堆可能返回 `unavailable`，不属于漏列 |
| `inspect_map` | 当前原生地图可查看或复用，受到原生按钮、旅行状态及遮挡限制；战斗中还要求可查看页面的时机 |

## 其余动作列表核对

`mcp_catalog.py` 默认公开 42 个工具。除始终可调用的 `get_observation` 外，其余 41 个公开工具名都能在 `GameAdapter.AvailableTools.cs` 中找到，没有发现某个工具完全未接入列表生成。此项只证明名称覆盖，不能替代各分支的行为验证。

逐组核对结果：

- 出牌、结束回合、药水、选牌、奖励、火堆、宝箱、商店、事件、先古之民、占卜、确认框、地图旅行与结算操作，都有对应状态或原生控件判断。暂未发现稳定单人场景下另一处明确的“能调用但整个工具名漏列”。
- 确认框、地图、尾声和结算分支会先清空底层动作，再添加当前页面的动作；这是防止对遮挡页面操作的必要处理。
- `close_card_view`、`close_map`、`set_selection_view` 已接入；是否列出取决于当前页面和原生返回／眼睛按钮。
- `get_observation`、可选 `capture_screenshot` 和测试入口不属于公开 `available_actions`，符合现行约定；截图不需要按场景添加。
- 结算分支只有在整个结算页 `Ready` 时才添加 `inspect_potions`，而药水请求直接判断 `PotionInspection.VisibleHolders()`。两处有条件差异；若文字或结算动画未完成但药水栏已可悬停，可能出现短暂漏列。尚未实测这一状态，应在统一查看规则时覆盖，不能据此断言稳定结算页有故障。

## 修复建议与验证要求

建议分三部分处理，避免将所有问题归为补充字符串：

1. **放宽遗物查看的房间限制。** 统一列表和调用使用的可见性谓词，覆盖普通事件、火堆、宝箱、奖励、选牌、地图及结算；逐场景确认原生是否允许悬停，被遮挡时仍拒绝。
2. **补齐非战斗牌组查看。** 以原生入口为准，连同页面生命周期和关闭后上下文一起实现；战斗专用手牌、牌堆和战斗对象不随之扩大。
3. **统一详情结果的动作上下文。** 建议所有详情结果提供 `available_actions`，打开或切换页面的工具须使用操作后的状态；从同一次观察获取状态令牌和动作列表，不额外读取并拼接可能变化的状态。无需附送完整观察。

第三部分需同时修改 Mod 序列化、Python 详情验证与字段投影；地图 `selectable` 预设和遗物 `summary` 当前重新构造顶层结果，也必须保留新增字段。手牌和选牌筛选则须确认空筛选不隐藏动作上下文。旧 Mod 没有该字段时不能伪造 `[]`，以免把“未知”变成“无可用操作”；应明确兼容规则。

扩大支持场景还会涉及 Python 观察校验：当前地图动作白名单不接受 `inspect_relics`，结算白名单也只接受结算操作、结算详情与药水详情。必须与 Mod 同步调整，否则合法的新动作会使整次观察变成 `transport_error`。确认框和其他遮挡规则应保留，不能通过取消全部验证解决。

验证应包含：各场景的原生入口与工具一致、列表与实际只读调用一致、遮挡与过渡不泄漏底层信息、页面关闭后恢复正确动作、详情预设／筛选保留上下文，以及详情后直接执行合法动作。当前审查只完成代码核对、程序集检查和 Python 投影复现，尚未实施这些修复或完成游戏实测。
