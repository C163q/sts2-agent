# 选牌详情的场景一致性修复

核对基线为提交 `0a53899`、Linux 游戏 `v0.107.1`（commit `59260271`）、RitsuLib `0.6.10`。修复版本为 Mod `0.34.0`、MCP `0.29.0`，基础观察结构仍为 `16`。

## 问题与处理

涅奥卷轴箱打开牌包选择后，基础观察和动作回执返回 `scene:"ancient"`，`inspect_selection` 却返回 `scene:"card_selection"`。隔离图形实例已复现；这属于字段语义不一致，未证明选择动作执行错误。

- `GameAdapter.SelectionRequest` 原来固定写入 `card_selection`，现复用请求前观察的 `scene`。
- Python 原来用该固定场景识别详情输出，现通过实际操作名保留全文及合并共享解释；MCP 和文件客户端均传入操作名。基础观察仍按原有可见信息边界过滤。
- 所有房间复用同一选牌入口，因此同一修复覆盖战斗、事件、火堆、商店、搜刮和宝箱等父场景。地图、牌组、牌堆查看会实际打开页面，仍使用各自已有文档定义的详情场景。

图形回归还发现测试框架比较整个身份响应，选牌时附带的 `selection_view` 会误报为更换对局。现仅提取 `process_id/session/run_id` 比较，身份变化检测仍保留。

## 验证结果与边界

- Python 294 项、C# 27 项通过；Mod 构建零警告、零错误。
- 一个游戏进程中五个新局通过：涅奥牌包、火堆锻造、发现选牌、事件牌组选择和商店删牌。检查场景与选择类型一致、全文及共享解释保留、详情读取前后基础观察不变。
- 每局保留待选择界面，由框架执行原生清理后进入下一局；正式游玩现场未参与测试。已核对牌包测试截图。
- `.env` 使用已存在的 Steam 游戏与创意工坊 RitsuLib 完整目录，已验证加载后可构建；个人路径不纳入 Git。

证据在忽略目录 `.tmp/2026-11-01-selection-scene/`：`gui-red/` 为原问题失败记录，`gui-green/` 为选牌断言通过但框架身份误判的记录，`gui-final/report.json` 为五局通过记录；另有 Python、C#、构建与环境构建日志。测试 DLL SHA-256 为 `a6ff24e0de78bb19a392a0df187126c60bca8fff6ec87503a62bc214c831b4c5`。
