## 当前用途与参数

`buy_item({item_id, preset?})`购买一件当前商店商品或启动删牌服务。item_id为外层商品整数ID，范围0到2147483647；preset为default/full，默认default。成功返回已是精简动作回执，包含期间事件及已知时的purchase_result。

卡牌、遗物、药水和删牌共用这个入口；原生处理金币、获取及附带效果。药水满栏／添水等原生领取失败返回failure_space／failure_forbidden，金币和商品保留；这与点击前被拒的illegal_action不同。

送货员补货沿用同一位置、分配新的商品ID，旧ID不能再次购买。删牌可以取消，确认后原生扣款并标记服务已用。购买触发选择或子奖励时先返回，使用当前页面工具继续。

## 待讨论的返回设计

需要继续输入时，buy_item目前没有purchase_result；后续确认、取消或子奖励完成也没有该字段。当前文档把它定义为“仅本次调用已知结果时存在”，因此这是现有契约下的设计取舍，不将其直接列成第四项确定缺陷；但工具说明“查看purchase_result判断结果”没有覆盖这些情况。

建议与claim_reward的待处理表达保持一致：购买流程尚未结束时，初次返回增加明确的待处理结果，例如：

```json
"purchase_result": {"item_id": 13, "status": "pending"}
```

这是候选字段节选，不是现有返回。pending表示仍需处理当前选择／奖励，不能据此断言金币尚未扣除：删牌和遗物的原生扣款时点不同。后续动作继续提供选择反馈及期间事件，默认不要求把购买终态跨调用附送；如需要统一补回success/canceled，应单独确定跟踪范围和生命周期。

## 参数与整理建议

维持单件item_id和default/full，不新增summary。建议修复四项优先问题，并在需要后续输入时增加上述pending；跨调用补回终态另行确定。现有回执已精简，购买上下文由inspect_shop提供。

购买的页面条件、商品ID定位、可交互性和失败原因应共用；需要区分原生领取失败与点击前拒绝，保留原生购买及补货流程。监听可集中到一个明确的购买过程，避免结果ID、监听对象和等待边界分散维护；这属于当前购买分支的小范围整理。

稳定性修复应针对仍在变化的独立UI动画，不能等待整个购买任务结束：变牌任务需要后续选牌才能结束。共用等待对其他输入边界的影响也须核对，避免把一次快照过期变成等待用户输入的超时。

## JSON及验证范围

[十八份实际完整JSON](2026-11-07-buy-item-examples/README.md)含十七份full、一份default。典型表现为：

| 场景 | 当前返回 |
| --- | --- |
| 普通卡牌／遗物／药水 | purchase_result:success，期间事件记录扣款及获取，保持精简回执 |
| 送货员补货 | 新商品ID可购买，旧ID被拒；该拒绝仍丢失许可 |
| 药水满栏／添水 | 正常动作回执带failure_space／failure_forbidden，金币及商品保留，之后可直接关闭 |
| 删牌确认／取消 | 初次choice_required，无purchase_result；后续取消或确认也无该字段，期间事件反映实际变化 |
| 子奖励／变牌 | 进入相应输入界面，无purchase_result；结束后的动作也不补购买结果 |
| 变牌后的快速选择 | 前两次运行在金币动画时stale；第三次正常完成，说明故障有时间窗口 |
| 金币不足、ID无效、页面覆盖等 | 同一个通用illegal_action，随后合法操作仍可能要求观察 |

药水满栏的实际字段节选为：

```json
{
  "transition": {"stop_reason": "action_completed", "complete": true, "events": []},
  "purchase_result": {"item_id": 10, "status": "failure_space"}
}
```

完整上下文见样例文件。50项相关Python通过；十种GUI场景分三批覆盖：首批八种通过、变牌失败；第二批诊断仍失败；最后变牌及假商人正常完成，不能记为单次十种全绿。首两次失败保留，产品问题仍存在。第三次没有触发测试中的等待恢复分支。

多人、第三方商店、全部价格／获取修改组合、真实超时和任意人工并发操作不新增穷举。当前工具不会因此自动获得这些场景的兼容保证。
