# 文档编写与维护规范

本文规定 sts2_agent 项目文档的分类、维护责任、阅读范围和写作要求。适用于仓库内自行维护的 Markdown 文档，包括 AGENTS.md、README.md、开发指南、接口说明、设计、调研、规格、计划、审阅和报告。

## 语言与表达

- 项目文档使用中文；API 名称、标识符、命令、路径和上游正式名称保留原文。代码示例中的注释使用英文。
- 优先使用清晰命名和直接表述，避免冗余注释、重复规则和无关背景。
- 明确区分已核实事实、已实现能力、已确认要求、候选方案和待验证问题；不能把计划写成现有能力。
- 安装、构建、启动和工具调用示例须与实际实现一致，并说明必要前提；未经验证的命令不能作为可用操作说明。

## 文档分类与日期命名

| 类型 | 维护责任 | 日期标识 |
| --- | --- | --- |
| 持续维护文档 | 随代码、资源、已确认规则或当前状态持续更新 | 不使用日期标识阶段，例如 `example.md` |
| 阶段性文档 | 对特定任务、阶段或代码基线负责，不承诺随后续代码持续更新 | 文件名或所属任务目录名包含精确到日的 `YYYY-MM-DD` |

- 文件名和所属任务目录名均无日期标识的文档，承担持续维护责任；不得用正文中的日期代替路径中的日期标识。
- 独立的阶段性文档使用 `YYYY-MM-DD-<topic>.md`。同一任务的阶段性文件可以放在含日期的任务专属目录中，内部使用 `progress.md` 等固定文件名，例如 `.superpowers/sdd/2026-10-24-example/progress.md`；引用和交付时保留含日期的任务路径。
- 调研、功能规格、实施计划、审阅、审计、执行记录和临时问题报告属于阶段性文档。路径日期表示所属任务或记录形成的日期，不因普通修订而反复更名；同日不同任务或文档用主题区分。
- 带日期不表示文档已经失效。本次正在实施的规格和计划仍是本次任务的依据；任务结束后，它们不再承担当前行为说明的责任。
- 持续维护文档可以记录已实现行为、已确认但尚未实现的要求和开放问题，但必须明确区分。

## 文档职责与唯一来源

| 位置 | 职责 |
| --- | --- |
| `README.md` | 项目定位、当前能力、使用入口和必要前提 |
| `AGENTS.md` | 简短、可执行的协作约定；详细规则通过链接引用 |
| `docs/documentation.md` | 文档编写与维护规范 |
| `docs/ai/` | 对应 AI 开发环境的专项约定，仅在适用环境和任务下阅读 |
| `docs/research/` | 带日期的调查记录，保留证据、适用版本、结论和未验证事项 |
| `docs/development/` | 持续维护实际构建、配置、Mod 加载、工具协议和错误语义；阅读入口见[开发文档索引](development/README.md) |
| 带日期的规格、计划、审阅和报告 | 对应任务的要求、执行依据及验证结果 |

- 同一规则或接口契约只保留一处完整定义，其他位置简述并链接；README 和 AGENTS 不复制详细规范。
- 当前 Mod、MCP、游戏及依赖兼容基线统一维护在 README；专题文档链接该基线，不重复版本声明。带日期的证据仍保留其核对版本。
- 实现、配置和测试是核对当前行为的依据；阶段性文档不能替代持续维护的现状说明。
- 仅为实际需要创建文档和目录，不预建空的文档体系。新增说明应从相关入口链接，内部链接使用相对路径。

## 游戏与上游资料

- 涉及游戏 API、Mod 加载、Godot 或社区库兼容性的结论，应记录核对日期、游戏版本与分支、相关依赖版本或提交，以及可定位的证据。
- 本地证据标明相对于游戏安装目录的文件路径及必要的类型或成员名；上游证据链接到作者维护的文档或源码，依赖具体实现时尽量固定到版本或提交。
- 分清游戏自带的加载入口与内部接口、Godot API、社区库扩展、本项目对外工具接口；不得将内部接口描述为官方承诺稳定的 API。
- 本机安装位置只能作为示例，不能写成所有开发者必须使用的路径；不将游戏程序集、资源、反编译产物、个人存档或密钥放入文档或仓库。
- 游戏或依赖更新时，重新核对受影响结论；保留阶段性调研的原始基线，新的当前结论写入持续维护文档或新的调研记录。

## 文档与实现冲突

发现持续维护文档与代码或资源冲突时，必须核实并处理。

1. 核对适用范围、相关资源和测试，明确实际行为与文档描述的差异。
2. 无论判断哪一方正确，都将文档中的实际行为描述同步为当前实现。若本次已经修复代码，则同步为修复后的行为；未能核实的部分明确标为待核实。
3. 无法确定哪一方正确，或认为文档可能正确、实现可能有误时，必须写问题报告。即使本次已经修复，也记录差异、修复和验证结果；修改文档本身不能算作实现问题已经解决。
4. 所有此类行为冲突都必须向用户说明差异、采取的处理及尚未解决的问题；存在报告时，提供报告路径。确认是文档过时且无须报告时，也必须说明已修正的差异。

问题报告默认放在不纳入 Git 的 `.tmp/YYYY-MM-DD-<topic>-report.md`，至少记录：

- 涉及的文档、代码、资源和核对基线；
- 原有描述或要求，以及核实到的实际行为；
- 判断依据、可能影响和仍需确认的问题；
- 已采取的修改、验证结果及当前处理状态。

报告属于阶段性文档，不承担现行规则说明的职责。需要跨任务持续跟进时，将报告同步到所属的规格说明或计划等文档。

## 历史文档的阅读范围

- 调研、阅读代码库和计划阶段，可以按需阅读过去的阶段性文档，以理解背景和查找证据；仍须用当前代码、资源和持续维护文档核对结论。
- 实现阶段只阅读本次需求相关的阶段性文档，以及这些文档明确引用的历史阶段性资料。
- 持续维护文档和源码不受上述历史资料限制；带日期但仍在本次任务范围内的规格、计划和审阅也不因日期较早而被排除。
- 本次规格和计划必须写全实施所需的最终决定，或明确引用必要资料。
- 实现中出现必须查阅范围外历史资料的新问题时，先明确调查问题，转回针对该问题的调研，核对当前证据并更新本次实施依据后再继续实现。

## 初见者有效信息

持续维护文档直接描述项目现状，不使用“本次实现”“本轮覆盖”等依赖会话或开发批次的指代；验证历史通过带日期、注明基线的记录引用。“本次请求／调用／快照”等有明确运行时指代的用法可以保留。

文档必须让首次阅读者理解适用范围、当前结论、执行要求和必要理由，无须了解此前对话、作者的思考过程或版本之间的修改经过。本原则适用于持续维护文档，也适用于阶段性规格、计划等文档。

- 用户决策说明与开发实现记录分开：前者用实际表现、影响、建议和必要示例说明待决定事项；内部类名、实现细节、问题编号及测试证据放入开发记录并链接。不得用内部术语堆砌或自造缩写代替解释。

- 删除不影响理解或执行的讨论过程、提议者身份和修订流水。例如，最终要求直接写“值为 18”，不写“最初为 15，后来用户要求改为 18”。规格和计划在实施期间发生修订时，直接更新要求及受影响步骤，不并列保留互相矛盾的旧指令。
- 保留会影响实施和维护的决策依据、限制、取舍与后果，并写在其作用范围内。例如，动作接口应说明适用场景、状态有效性要求和失败语义。
- 审阅、审计、问题报告中的复现条件、核对基线、差异和验证证据属于有效信息；用明确的检查结论组织内容，不复述无关对话。
- 未实现的候选应写明候选内容、依赖、限制和待决定事项，不用“用户觉得不错，先记录”等措辞代替设计信息。
- 项目专有名词必须先核对正式名称，使用资源定义或所属持续维护文档中的名称；不得自行创造简称或别称。已确认的正式简称确需使用时，先给出与完整名称的对应关系。此要求同时适用于文档和对用户的说明。

## 进度文档

包含任务勾选、任务表或其他实施进度记录的文档，必须在同一文档开头保留总结性进度说明，不能只提供分散的任务状态或让读者转到另一份文件判断整体进度。

此要求同时适用于含任务进度的计划和 `progress.md` 等执行记录，不因文件被 Git 忽略而免除。不记录实施进度的规格、调研或审阅文档，无须复制任务进度总结。

总结至少说明总体状态、已完成和剩余范围、当前步骤及阻塞情况；有明确任务总数时，同时注明完成数与总数。例如：

> 当前状态：实施中。共 6 项，已完成 4 项；正在处理存档校验，剩余错误反馈与最终验证。暂无阻塞。

- 任务状态变化、暂停交接和完成时，同步更新总结与明细。
- 结束时说明已完成、已取消或仍有遗留；遗留问题写明范围和去向。
