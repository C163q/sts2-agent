# 文档编写与维护规范

本文规定文档的读者、分类、维护责任、阅读范围和写作要求，适用于仓库内自行维护的 Markdown 文档。

## 读者与内容范围

| 文档 | 主要读者 | 内容与知识预设 |
| --- | --- | --- |
| 项目根目录 `README.md` | 项目用户 | 项目定位、能力、必要前提、安装与使用；库项目包括公共 API 的用法。源码开发、内部架构、测试与协作流程放入开发文档 |
| 其他持续维护文档 | 开发者，包括首次接触项目的开发者 | 说明适用范围、必要概念、操作或维护入口，补足项目特有的背景知识 |
| 阶段性文档 | 对应任务或阶段的参与开发者 | 可以预设熟悉项目；写清任务目标、适用基线、结论和执行依据 |

按读者的任务选择信息和解释深度。面向用户的决策说明用实际表现、影响、建议和必要示例表达；开发细节与验证证据放在相应开发记录中并链接。

## 语言与表达

- 项目文档使用中文；API 名称、标识符、命令、路径和上游正式名称保留原文。代码示例中的注释使用英文。
- 直接说明含义、范围、条件和结果；删去同义复述、无关背景和可由前文直接推出的排除项。
- 加入否定声明或纠偏式对比前，先判断它是否提供影响理解、使用或决策的信息。真实限制和失败条件可直接写明；预防误解的说明应有用户提问、实际误用或已记录事件作为依据。
- 明确区分已核实事实、已实现能力、已确认要求、候选方案和待验证问题。
- 使用项目正式名称；必要的术语和简称在首次使用时说明，并与资源定义或所属文档一致。对用户的说明也遵循此要求。
- 安装、构建、启动和接口调用示例须说明必要前提，并核对实际实现与执行结果；未验证部分明确标注。

## 文档分类与日期命名

| 类型 | 维护责任 | 日期标识 |
| --- | --- | --- |
| 持续维护文档 | 随代码、资源、已确认规则或当前状态持续更新 | 不使用日期标识阶段，例如 `example.md` |
| 阶段性文档 | 对特定任务、阶段或代码基线负责，不承诺随后续代码持续更新 | 文件名或所属任务目录名包含精确到日的 `YYYY-MM-DD` |

- 文件名和所属任务目录名均无日期标识的文档，承担持续维护责任。
- 独立的阶段性文档使用 `YYYY-MM-DD-<topic>.md`。同一任务的阶段性文件可以放在含日期的任务专属目录中，内部使用 `progress.md` 等固定文件名，例如 `docs/tasks/2026-10-24-example/progress.md`；引用和交付时保留含日期的任务路径。
- 调研、功能规格、实施计划、审阅、审计、执行记录和临时问题报告属于阶段性文档。路径日期表示所属任务或记录形成的日期，不因普通修订而反复更名；同日不同任务或文档用主题区分。
- 规格和计划在所属任务实施期间仍是执行依据；任务结束后，当前行为说明由持续维护文档承担。

## 文档组织与唯一来源

- 同一规则或接口契约只保留一处完整定义，其他位置提供读者所需的简述并链接。
- 按信息性质选择维护位置：字段、默认值等可推导事实优先由类型、配置或生成的参考资料维护；局部实现细节放在代码及必要注释中；跨模块契约、使用流程和决策依据写入相应文档。
- 开发指南应连接职责、流程与关键代码入口，便于读者定位和修改实现。
- 按实际需要创建文档和目录。新增说明从相关入口链接，内部链接使用相对路径；移动或合并内容时同步修复引用。

文档变更按内容核对链接、路径、示例和相关实现。交付时说明验证结果与未验证范围；反复过时的内容应检查是否存在重复维护，或适合从源数据生成。

## 文档与实现冲突

发现持续维护文档与代码或资源冲突时，必须核实并处理。

1. 核对适用范围、相关资源和测试，明确实际行为与文档描述的差异。
2. 将实际行为描述同步为当前实现；已经修复代码时，描述修复后的行为。已确认的要求保留为要求，并注明实现差距；未能核实的部分标为待核实。
3. 无法确定哪一方正确，或认为实现可能有误时，必须写问题报告；已修复的问题也记录差异、修复和验证结果。
4. 向用户说明差异、采取的处理及尚未解决的问题；存在报告时提供路径。

问题报告默认放在不纳入 Git 的 `.tmp/YYYY-MM-DD-<topic>-report.md`，至少记录：

- 涉及的文档、代码、资源和核对基线；
- 原有描述或要求，以及核实到的实际行为；
- 判断依据、可能影响和仍需确认的问题；
- 已采取的修改、验证结果及当前处理状态。

需要跨任务持续跟进的问题，同步到所属的规格说明或计划等文档。

## 历史文档的阅读范围

- 调研、阅读代码库和计划阶段，可以按需阅读过去的阶段性文档，以理解背景和查找证据；仍须用当前代码、资源和持续维护文档核对结论。
- 实现阶段只阅读本次需求相关的阶段性文档，以及这些文档明确引用的历史阶段性资料。
- 持续维护文档和源码按任务需要阅读。
- 本次规格和计划必须写全实施所需的最终决定，或明确引用必要资料。
- 实现中出现必须查阅范围外历史资料的新问题时，先明确调查问题，转回针对该问题的调研，核对当前证据并更新本次实施依据后再继续实现。

## 内容取舍与修订

文档应让目标读者理解适用范围、结论、执行要求和必要理由，无须还原此前对话。

- 持续维护文档围绕当前适用的行为、要求和开放问题组织。修订说明、规格或计划时，直接更新最终内容及受影响步骤，删去无助于理解或执行的讨论过程、提议者身份和修订流水。
- 保留影响实施和维护的决策依据、限制、取舍与后果，写在其作用范围内。
- 审阅、审计和问题报告用检查结论组织复现条件、核对基线、差异和验证证据；验证历史通过带日期、注明基线的记录引用。
- 候选方案写明内容、依赖、限制和待决定事项。

## 进度文档

包含任务勾选、任务表或其他实施进度记录的文档，必须在同一文档开头保留总结性进度说明。含进度的计划、`progress.md` 等执行记录及被 Git 忽略的文件均适用。

总结至少说明总体状态、已完成和剩余范围、当前步骤及阻塞情况；有明确任务总数时，同时注明完成数与总数。例如：

> 当前状态：实施中。共 6 项，已完成 4 项；正在处理存档校验，剩余错误反馈与最终验证。暂无阻塞。

- 任务状态变化、暂停交接和完成时，同步更新总结与明细。
- 结束时说明已完成、已取消或仍有遗留；遗留问题写明范围和去向。
